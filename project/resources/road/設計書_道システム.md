## 1. 目的と設計方針

レールの下に「ヨッシークラフトワールド風の道」を表示するシステム。3つの方針で設計する。

1. **レールが唯一の真実 (Single Source of Truth)**
   道の形・プレイヤーの移動・敵のパトロール・カメラは、すべて SplineRail から
   同じ関数で取得したフレーム(位置+向き)を使う。見た目と挙動が絶対にズレない。
2. **静的なものはロード時に作り、毎フレームは何もしない**
   道メッシュは編集時/ロード時に1回生成して固定。実行時コストはドローコールのみ。
3. **動くものだけスキンモデルで曲げる**
   毎フレーム形が変わるギミックに限り、ボーン入りモデルをレールで駆動する。

## 2. 全体構成

```
SplineRail (ノード列)
   │ 編集時に1回構築
   ▼
FrameCache (0.25m刻みの 位置+right+up+tangent テーブル)
   │ GetFrameAtDistance(d) … 実測 17ns/回
   ├─→ プレイヤー移動 / 敵パトロール / カメラ     (毎フレーム参照)
   ├─→ RoadMeshBuilder → 静的道メッシュ           (ロード時1回)
   └─→ ボーン駆動 → スキンモデル                  (動的ギミックのみ)
交差点/分岐/終端 = モデルピース (2mグリッド配置)
```

## 3. SplineRail::GetFrameAtDistance 仕様

### API
```
struct RailFrame { Vector3 position, right, up, tangent; };
RailFrame GetFrameAtDistance(float d);   // d: レール始点からの距離[m]
```

### 内部実装 (FrameCache)
- レール編集確定時に、始点から 0.25m 刻みで全フレームを計算してテーブル化
- フレーム計算は RMF (平行移動フレーム):
  - `right(0) = normalize(cross(worldUp, tangent(0)))`
  - `right(i) = normalize(right(i-1) - dot(right(i-1), T(i)) * T(i))`
  - `up(i) = cross(T(i), right(i))`
  - 接線が水平寄り(|T.y|<0.7)のときは理想rightへ15%/step戻す(ロール回復)
- 実行時は `d/0.25` でテーブルを引いて線形補間 + 正規化
- **再構築タイミング**: ノード編集・溶接・なめらか化の確定時のみ

### コスト (実測ベンチ)
| 方式 | 1回あたり | 50回/フレーム |
|---|---|---|
| 毎回スプライン計算 | 59.7 ns | 0.0030 ms |
| FrameCache参照 | 17.1 ns | 0.0009 ms |

メモリ: 16mレールで約3KB、7本で約21KB。

## 4. 静的道: RoadMeshBuilder 仕様

### 入出力
- 入力: FrameCache済みの SplineRail 1本
- 出力: 頂点/インデックスバッファ各1本 (= レール1本1ドローコール)
- テクスチャ: road_atlas.png (全道要素で共有・1枚)

### 生成アルゴリズム (確定版)
1. **曲率適応サンプリング**: 元カーブを0.05m刻みで歩き、
   「方向変化の累積>3° かつ 0.06m以上進んだ」or「1.0m進んだ」でリングを置く
   (実測: 均一0.15mの半分のリング数で同等の滑らかさ)
2. 各リングで FrameCache からフレーム取得
3. **断面プロファイル展開** (12頂点、下表)。法線はフレームから解析的に:
   `n = right*nr + up*nu` (面法線は使わない=スムーズシェーディング)
4. **内側折返しの溶接**: `dot(newPos - prevRing同頂点, tangent) < 0` なら前位置に溶接
5. **坂UV切替**: |tangent.y|>0.40 (24°) で上面2頂点のvを坂帯へ。
   境目は同位置リングを2重化、判定は入り0.45/抜け0.35のヒステリシス
6. リング間に6帯×2三角形を張る。u = 累積距離 / 2.0
7. 両端に road_end モデルを接線向きで自動配置 (始端は180°回転)

### 断面プロファイル (X=lateral, Z=height / エンジンではright,up方向)
| # | 用途 | lat | h | UV v | 法線(nr,nu) |
|---|---|---|---|---|---|
| 0/1 | 左壁 下/上 | -1.00 | 0.00/0.15 | 0.5352/0.6992 | (-1,0) |
| 2/3 | 左ベベル 下/上 | -1.00/-0.88 | 0.15/0.25 | 0.7070/0.7422 | (-0.64,0.77) |
| 4/5 | 上面 左/右 | ∓0.88 | 0.25 | 平:0.750/1.000 坂:0.0234/0.2031 | (0,1) |
| 6/7 | 右ベベル 上/下 | 0.88/1.00 | 0.25/0.15 | 0.7422/0.7070 | (0.64,0.77) |
| 8/9 | 右壁 上/下 | 1.00 | 0.15/0.00 | 0.6992/0.5352 | (1,0) |
| 10/11 | 底 左/右 | ∓1.00 | 0.00 | 0.4727/0.5273 | (0,-1) |

## 5. モデルピース (2mグリッド用)

グリッドで組む場所(交差点・分岐・広場)に使用。全開口の断面は§4と同一(数値検証済み)。

| ファイル | 三角形 | 用途 / 原点 |
|---|---|---|

| road_corner | 64 | 90°カーブ / タイル中心、開口+X+Y |

## 6. スキンモデル (動的ギミック・装飾用)

### ファイル仕様
| ファイル | ボーン | 頂点/三角形 | 用途 |
|---|---|---|---|
| road_skinned_8m.glb | 17 (0.5m間隔) | 396 / 384 | 動く床・長い装飾 |
| road_skinned_2m.glb | 5 (0.5m間隔) | 108 / 96 | 短い区間・端数埋め |

- レストポーズ: 直線 (+Y方向)。ウェイトは隣接2ボーンの線形ブレンド
- 断面・UV・アトラスは§4と完全共通 → 静的道と見た目が揃う
- GLB読み戻し+スキニングシミュレーションで動作検証済み (skinned_bent.png)

### ボーン駆動 (エンジン側の処理)
```
配置距離 d0 のセグメントについて、各ボーン k (レスト位置 = k*0.5m):
  frame = rail.GetFrameAtDistance(d0 + k*0.5)
  boneWorld[k] = { X列=frame.right, Y列=frame.tangent, Z列=frame.up, T列=frame.position }
  スキン行列 = boneWorld[k] * inverseBind[k]   // 既存のSkinnedMeshと同じ
```
- 隣接セグメントの境界ボーンは同じdの同じフレーム → **境界は自動的にシームレス**
- 静的レールなら行列更新は配置時1回。動くレール(振幅XYZ)は剛体なので
  ワールド行列側で動かす(ボーン更新不要)

### 使いどころ / 使わないところ
- ○ 毎フレームうねる床、波打つ橋、レール沿いのロープ/フェンス/ツタ/キャタピラ敵
- × 静的な道 (RoadMeshBuilderの方が軽く、適応サンプリング・坂UVも使えるため)

## 7. パフォーマンス予算

計測環境の現状: FPS 56 / フレーム 17.7ms / Update 0.98ms / Draw 0.88ms /
ドローコール 70 / VRAM 17MB(7385MB中)

| 項目 | コスト | フレーム比 |
|---|---|---|
| フレーム取得 50回/f | 0.0009 ms | 0.005% |
| 道メッシュ 7本 (VB+IB) | 0.4 MB VRAM | 0.005% |
| アトラスv5 (mips込) | 5.3 MB VRAM | 0.07% |
| FrameCache 7本 | 21 KB RAM | — |
| スキンギミック1個の行列更新 | 〜1 KB / 数百ns | 誤差 |
| ノード編集時の道再生成 | < 1 ms (編集時のみ) | 0 (実行時) |

**結論: 道システムは予算をほぼ消費しない。** 今後FPSが落ちる場合の容疑者は
ポストエフェクト/GPUパーティクル量/ドローコール増加/スキンキャラ数。
推測せずパフォーマンスモニターで計測してから対処する。

## 9. ジャンクション生成 (共有ノードの接続)

レール同士がつながるノード(端点溶接=曲がり角 / 途中連結=T字 / 交差=十字)は
「ジャンクションパッチ」で接続する。詳細は guides/GUIDE_ジャンクション生成.md。

- 各道はノードの t_cut 手前で止め、隙間をパッチ(上面扇+ベベル+壁+底)で埋める
- 隣接方向の角度で マイター(<175°) / 直進(〜185°) / 円弧(>185°) を切替
- 任意本数・任意角度を同一コードで処理。入口断面は§4と一致(誤差0を検証済み)
- パッチ1個 180〜250三角形、生成は編集時のみ
- 運用ルール: 共有ノード前後1.5mはレールを平坦にする
- ゆるい2本溶接(150°以上)はパッチより連続パス生成の方が滑らか
- タスク: T9 ジャンクション検出+道のカット(4h) / T10 パッチ生成(8h) を Must に追加

## 10. 穴区間 (赤レール) の見た目

「穴」フラグ区間は専用モデルではなく生成で表現する。詳細は 仕様書_穴区間の見た目生成.md。
- 道メッシュを区間で途切れさせ、両端に road_end を自動配置 (追加アセットなし)
- 手前後 1.0m の上面を危険帯 (v=0.2070〜0.2734, アトラスv5) に切替
- 落下判定と見た目は SplineRail::GetHoleIntervals() を共通参照 (ズレ防止)
- タスク: T11 GetHoleIntervals + 穴スキップ + キャップ配置 (4h) を Must に追加

## 11. 自動レール接続とジョイント表示

プラレールのように端点を近づけるだけで自動接続し、接続点に凸ジョイント
(road_joint.glb, 136三角形, アトラス共有) を表示する。詳細は 仕様書_自動レール接続.md。
- スナップ検出→既存の溶接/連結処理を呼ぶだけ (接続ロジックは追加しない)
- ジョイントは保存しない派生データ。InstancedGroupで全個+1ドローコール
- エディタに接続一覧タブ (選択ハイライト / 切断 / Ctrl-Z統合)
- タスク: T12 スナップ+プレビュー (4h) / T13 ジョイント配置+管理UI (4h)
- 追加 (仕様書§8-9): T14 レール毎の道ON/OFF (4h) /
  T15 編集中パフォーマンス修正 = 固定容量バッファ+差分再生成+軽量プレビュー (8h, 最優先)
